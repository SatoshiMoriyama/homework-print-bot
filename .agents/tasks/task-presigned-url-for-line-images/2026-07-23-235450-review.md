# Presigned URL utility for sending print images to LINE

The change adds an S3 presigned URL utility (`getPresignedUrl`) and a `sendPrintImage` function that combines URL generation with LINE's push-message API to deliver generated print images to users. Both original and preview URLs use the same presigned URL, which works for now but will need a separate thumbnail path eventually.

Watch for:
- Presigned URL TTL of 1 hour may be too short if LINE re-fetches the image later (confirmed — hardcoded default with no LINE-specific consideration).
- `sendPrintImage` has no caller yet — exported but dead code until a print-generation flow invokes it (confirmed).
- No error handling around the `pushMessage` call; failures propagate as unhandled rejections to whatever invokes `sendPrintImage` (confirmed).

## High-level view

The presigned URL utility wraps `GetObjectCommand` + `getSignedUrl` with a configurable TTL defaulting to one hour. The one-hour window is the main concern: LINE may re-fetch image URLs well after delivery, and expired URLs produce broken images in the chat history.

`sendPrintImage` reads `BUCKET_NAME` from the environment on every call, meaning a missing env var only surfaces at runtime. The function uses `pushMessage` (not `replyMessage`), enabling asynchronous delivery outside the webhook request lifecycle, but has no logging or error wrapping — failures from rate limits, invalid userIds, or network errors will be hard to diagnose from the caller.

The same presigned URL serves both `originalContentUrl` and `previewImageUrl`. LINE clients download the full image even for the thumbnail, which becomes a bandwidth concern once print images are large.

## Presigned URL TTL and LINE's image lifecycle

The default TTL of 3600 seconds (1 hour) is set in `shared/s3.ts` and used without override in `sendPrintImage`. LINE's Messaging API documentation states that image URLs in messages should remain accessible — LINE servers may re-fetch them for display when a user opens the chat later. If the URL expires before LINE's CDN caches the content (or if the CDN evicts it), the image will appear broken in the conversation.

```typescript
const DEFAULT_EXPIRES_IN = 3600;
```

The `expiresIn` parameter is configurable, so fixing this is straightforward: either increase the default or pass a longer TTL from `sendPrintImage`. The trade-off is security exposure (longer-lived URLs leak access to S3 objects for longer), but since these are user-owned print images rather than sensitive data, a 6-24 hour window is reasonable.

## sendPrintImage — delivery without observability

If `getPresignedUrl` or `client.pushMessage` throws, there's no logging or wrapping:

```typescript
export async function sendPrintImage(userId: string, s3Key: string): Promise<void> {
  const bucketName = process.env.BUCKET_NAME;
  if (!bucketName) {
    throw new Error('Environment variable "BUCKET_NAME" is not configured');
  }
  const presignedUrl = await getPresignedUrl(bucketName, s3Key);
  const client = await getLineClient();
  await client.pushMessage(userId, {
    type: "image",
    originalContentUrl: presignedUrl,
    previewImageUrl: presignedUrl,
  });
}
```

When called from an async print-generation pipeline (Step Functions, EventBridge, another Lambda), a raw SDK error from `pushMessage` (rate limit, invalid userId, network timeout) will be harder to diagnose without structured logging at this layer. Since `sendPrintImage` is the delivery boundary, it's the natural place to add observability.

## Test coverage gaps

- `sendPrintImage` has no test coverage. The env-var guard, the composition of `getPresignedUrl` + `pushMessage`, and the message shape are all unverified.
- The tests mock both SDK modules at the module level, confirming call passthrough only. An integration test (or at least a unit test of `sendPrintImage` with mocked dependencies) would verify the composition.
