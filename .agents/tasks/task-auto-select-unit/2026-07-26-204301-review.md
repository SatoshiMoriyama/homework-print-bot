# Auto-select next unit based on child learning progress

The handler no longer hardcodes `addition_no_carry / difficulty 1 / 8 questions` when invoking print generation. Instead, when no explicit `subcategory` is provided in `params`, the agent fetches the child's `current_unit_order` from the CHILDREN_TABLE and delegates to `determine_next_problem()` to pick the appropriate unit, difficulty, and question count based on learning stats. Explicit params still work unchanged for the `regenerate_print` path and any future caller that knows what it wants.

**Watch for:** Silent exception swallowing in `_get_child_current_unit_order` hides DynamoDB failures behind a fallback (confirmed). The `current_unit_order` stored in CHILDREN_TABLE is never updated by this change, so advancement decisions made by `determine_next_problem` (the `should_advance` flag) have no lasting effect between invocations (confirmed).

## High-level view

The TypeScript handler drops the hardcoded params and sends a minimal `{ action, child_id }` payload. The Python entrypoint branches on whether `params.subcategory` is present: if yes, backward-compatible explicit path; if no, it calls into the adaptive learning agent to determine what to generate next.

The `_get_child_current_unit_order` helper reads from DynamoDB with a bare `except Exception: pass`, meaning any transient DynamoDB failure (throttle, network timeout, permission error) silently falls back to unit 1 rather than surfacing the problem. For a first-grader who's progressed to unit 12, this would silently regress them to counting numbers with no indication anything went wrong.

`determine_next_problem` computes `should_advance = True` when the child has mastered the current unit, but nothing in this change writes the new `current_unit_order` back to CHILDREN_TABLE. The advancement works because `determine_next_problem` re-derives the decision from learning stats each time, but `current_unit_order` remains permanently stale. If any other code path (dashboard, progress report, parent-facing API) reads that field, it will show outdated progress.

## Branching on `params.subcategory` presence

The branching condition `if params.get("subcategory")` means an empty string also triggers the auto-select path. The explicit path doesn't validate that the provided subcategory actually exists in the unit list — `_get_unit_label` returns the raw string as a fallback, and `generate_print` will attempt to generate questions for an invalid subcategory, pushing the failure to the LLM layer with no structured error.

The conditional import of `determine_next_problem` inside the else-branch avoids a circular import (`adaptive_learning.agent` imports `_get_unit_label` from entrypoint).

## `_get_child_current_unit_order` error handling

```python
try:
    response = table.get_item(Key={"child_id": child_id})
    item = response.get("Item")
    if item:
        return int(item.get("current_unit_order", 1))
except Exception:
    pass
return 1
```

The function conflates three distinct failure modes into a single fallback: child not found (correct to default), DynamoDB error (should be surfaced), and malformed data where `current_unit_order` can't be cast to int. A `ClientError` catch for DynamoDB-specific errors with logging would preserve the graceful fallback for missing children while making operational failures visible.

## State advancement gap

`determine_next_problem` returns `should_advance: True` and computes the next subcategory in-memory, but the caller (`handle_generate_print`) discards the `should_advance` flag — it only extracts `category`, `subcategory`, `difficulty`, `question_count`, and `weak_areas`. If any other code path reads `current_unit_order` expecting it to reflect actual progress (e.g., a parent notification saying "your child is on unit 7"), it will be wrong.

## Test coverage

Not tested: the case where `determine_next_problem` raises an exception (currently propagates as an unhandled 500); the case where `determine_next_problem` returns a malformed dict missing required keys; interaction between advancement logic and the entrypoint's variable extraction.
