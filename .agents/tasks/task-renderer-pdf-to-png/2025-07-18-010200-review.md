# PDF 経由 PNG 生成への切り替え（Renderer Lambda）

Renderer Lambda の出力パイプラインを `page.screenshot({ fullPage: true })` から PDF 中間形式（`page.pdf()` + `pdf-to-png-converter`）に切り替え、複数ページ対応を追加した変更。A4 フォーマット固定で PDF を生成し、各ページを個別 PNG として S3 にアップロードする。後方互換性のため既存の `pngS3Key` フィールドは最初のページを返し、新規の `pngS3Keys` 配列で全ページを返す。

**Watch for:** `pdfToPng` が空配列を返した場合の `pngS3Keys[0]` が `undefined` になるパス（confirmed）。`networkidle0` への変更が Lambda タイムアウトリスクを増やす点（likely）。`pngS3Keys` が呼び出し元（webhook handler）で未使用のまま残っている点（confirmed、ただし後方互換設計なので意図的かもしれない）。

## High-level view

PDF 中間形式を挟むことで、Puppeteer の `fullPage` スクリーンショットではコンテンツ量に応じて縦に伸びていた出力が A4 ページ単位に分割される。

後方互換性は `pngS3Key`（= 最初のページ）を維持しつつ `pngS3Keys` 配列を追加する形で確保されている。ただし shared の `RendererResult` 側では `pngS3Keys` が optional（`?`）なのに対し、Lambda の `RendererResponse` では required。呼び出し元の webhook handler は依然 `pngS3Key` のみ参照しており、マルチページの恩恵はまだ受けていない。

`pdfToPng` は browser close の外で呼ばれるため Chromium リソースは安全に解放されるが、変換失敗時のエラーは呼び出し元にそのまま伝播し、部分アップロード状態の PNG が S3 に残る可能性がある。

<summary>Issues (4)</summary>

1. **空ページガード欠如** — `pdfToPng` が空配列を返すと `pngS3Keys[0]` は `undefined` になり、呼び出し元は不正な S3 キーを受け取る。変換後に `pngPages.length === 0` チェックを追加してエラーを投げるべき。
2. **networkidle0 タイムアウトリスク** — `waitUntil` が `domcontentloaded` から `networkidle0` に変更された。外部リソースを持つ HTML やネットワーク遅延がある場合、500ms の無通信待機が累積して 60 秒の Lambda タイムアウトに近づく。タイムアウト付き fallback か、`networkidle2` への変更を検討。
3. **部分アップロードのクリーンアップ欠如** — マルチページアップロードのループ途中で S3 PutObject が失敗すると、先にアップロードされたページが孤立する。冪等性の観点から問題になりうる。
4. **viewportScale 未指定** — `pdfToPng` のデフォルト `viewportScale` は `1` で、A4 ページ（595×842 PDF ポイント）を 595×842 px の PNG に変換する。プリントワークシートとして十分な解像度かどうか確認が必要。

## pdfToPng 空配列と undefined アクセス

`pdfToPng(pdfBuffer)` が空配列を返すケース（破損 PDF、ゼロページ PDF）に対するガードがない。

```typescript
const pngPages = await pdfToPng(pdfBuffer);
// pngPages.length === 0 の場合...
for (let i = 0; i < pngPages.length; i++) { ... }
// ループは実行されない → pngS3Keys = []
return {
  pngS3Key: pngS3Keys[0],  // undefined
  pngS3Keys,               // []
};
```

`RendererResponse` は `pngS3Key: string` を宣言しているが、実際に `undefined` が返る。呼び出し元の webhook handler が `rendered.pngS3Key` を `sendPrintImage` にそのまま渡すため、S3 キーが `undefined` の画像を LINE に送信しようとしてダウンストリームでエラーになる。

## networkidle0 への waitUntil 変更

`domcontentloaded` から `networkidle0` に変更されている。`networkidle0` は 500ms 間にネットワークリクエストがゼロになるまで待つ。HTML テンプレートが外部 CSS/フォント/画像を参照している場合や、Lambda の VPC 構成によっては待機時間が大幅に増える。Lambda のタイムアウトは 60 秒で、Chromium 起動 + フォントコピー + ページレンダリング + PDF 生成 + PNG 変換 + S3 アップロードの全工程がこの中に収まる必要がある。

失敗モードが「不完全な見た目」から「Lambda タイムアウト」に変わる。`networkidle2`（2 リクエスト以下で idle）がより安全な中間地点。

## 部分アップロードとエラー伝播

マルチページアップロードは sequential な for ループで実装されている。3 ページ中 2 ページ目の `PutObject` が失敗した場合：

- 1 ページ目は S3 に残る
- エラーが呼び出し元に伝播する
- リトライ時に 1 ページ目が再アップロードされる（冪等だが帯域の無駄）

致命的ではないが、孤立ファイルの蓄積が気になるなら TTL ベースの S3 ライフサイクルルールが有効。

## PNG 解像度（viewportScale）

`pdfToPng` はデフォルト `viewportScale: 1` で動作する。A4 の PDF ポイントサイズ（595×842）がそのまま PNG のピクセル数になるため、96 DPI 相当。プリントワークシートを実際の印刷機に送る場合や、高解像度ディスプレイで表示する場合には不足する可能性がある。`viewportScale: 2`（192 DPI 相当）を指定すれば改善するが、Lambda のメモリ消費（2048MB）とのトレードオフになり実測が必要。

## テストカバレッジの欠落

テストされていないパス：
- `pdfToPng` が空配列を返すケース
- `pdfToPng` が例外を投げるケース（browser close 後に発生するためブラウザリークはないが、エラーメッセージの品質が未検証）
- `PutObject` がマルチページアップロード途中で失敗するケース
- `PngPageOutput.content` が `undefined` のケース（型定義では `content: Buffer | undefined`）
