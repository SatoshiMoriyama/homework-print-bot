# Lambda + Puppeteer による HTML→PNG レンダリング

Webhook Lambda から同期呼び出しされる専用の Node.js Lambda を追加し、S3 上の HTML プリントを PNG に変換して LINE で画像表示可能にする変更。AgentCore 側は Playwright が使えない環境を検知すると HTML のまま S3 に保存し `needs_rendering: true` フラグを返す。Webhook がこのフラグを受け取るとレンダラ Lambda を invoke し、返却された PNG キーで署名付き URL を生成する。

**Watch for:** `@sparticuz/chromium` を NodejsFunction の bundling でそのままバンドルすると Lambda のデプロイパッケージサイズ制限に抵触する可能性が高い (confirmed)。`networkidle0` と外部フォント読み込みの組み合わせで Lambda タイムアウトに至るリスクがある (likely)。`needs_rendering` フローの webhook テストがない (confirmed)。

## High-level view

CDK コンストラクトは `NodejsFunction` の `bundling` に `minify: true` のみ指定しているが、`@sparticuz/chromium` は native バイナリを含む大きなパッケージであり、esbuild でそのままバンドルすることはできない。Lambda Layer として分離するか、`bundling.nodeModules` に含めて install させる必要がある。

Python 側の HTML 検出ロジックは `handle_generate_print` と `handle_regenerate_print` に完全に重複したコードブロックとして存在している。抽出すればメンテナンスコストが下がる。

`sendPrintImage` 内で `BUCKET_NAME` の取得方法がモジュールレベル定数から `process.env` 直接読み取りに変更されており、同一ファイル内の他箇所と不整合がある。

## Chromium パッケージングと Lambda デプロイサイズ

CDK コンストラクト (`packages/infra/lib/constructs/renderer.ts`) は `NodejsFunction` を使い、`bundling` に `minify: true` と `sourceMap: true` のみを指定している。

```typescript
bundling: {
  minify: true,
  sourceMap: true,
},
```

`@sparticuz/chromium` は Chromium バイナリ (~50MB brotli 圧縮済み) を `node_modules` 内に持つパッケージであり、esbuild の通常バンドルでは native ファイルが含まれない。Lambda にデプロイしても Chromium バイナリが存在せず `executablePath()` が失敗するか、あるいはバンドルサイズが 250MB の上限を超過する。

対処パターンは二つ:

1. `bundling.nodeModules: ["@sparticuz/chromium", "puppeteer-core"]` を指定し、esbuild がこれらを外部モジュールとして扱い、代わりに `npm install` で `node_modules/` フォルダに配置させる
2. `@sparticuz/chromium` を Lambda Layer として独立デプロイし、`layers` プロパティで参照する

どちらも採用されていない現状では、デプロイ時に実行できない Lambda が作成される (confirmed — CDK のコード上に対処がない)。

## networkidle0 と外部リソース依存

レンダラ Lambda は `setContent` で `waitUntil: "networkidle0"` を使用している。ネットワーク接続がゼロになるまで 500ms 待つオプションであり、HTML が外部リソース（Google Fonts の CSS/woff2）を参照している場合、そのダウンロード完了を待つことになる。

Issue の技術詳細に「Noto Sans JP（Google Fonts から読み込み or Layer に同梱）」と記載されている。Google Fonts からの読み込みを選択した場合、Lambda のネットワーク構成によっては DNS 解決・HTTPS 接続に数秒〜数十秒かかる。コールドスタート + Chromium 起動 + フォントダウンロードが重なると 60 秒タイムアウトに達しうる (likely)。

`waitUntil: "domcontentloaded"` に変更しフォントのロードを待たない、あるいは HTML テンプレート内に Base64 フォントをインライン化するのが安全策。

## needs_rendering パスのテスト欠如

`packages/functions/src/webhook/handler.test.ts` は `invokeRenderer` をモックで差し替えているが、`handleTextMessage` 内で `result.needs_rendering === true` の場合にレンダラが呼ばれ `s3Key` が更新されることを検証するテストが存在しない (confirmed)。

レンダラ呼び出しが失敗した場合の挙動も未検証。現在の実装では `invokeRenderer` が throw すると外側の `catch (err)` でユーザに「エラーが発生しました」と返すフローに入るが、これが意図通りかテストで担保されていない。

## Python HTML 検出の重複とヒューリスティック

`handle_generate_print` と `handle_regenerate_print` の両方に以下の同一パターンが存在する:

```python
try:
    html_decoded = png_bytes.decode("utf-8")
    if html_decoded.strip().startswith("<!DOCTYPE html>") or html_decoded.strip().startswith("<html"):
        needs_rendering = True
        ...
except (UnicodeDecodeError, AttributeError):
    ...
```

ヘルパー関数 `detect_content_type(data: bytes) -> tuple[str, str, bool]` のようなものに抽出すべき。

ヒューリスティックの堅牢性について：将来 `render_to_png` が SVG やテキストベースのフォーマットを返す可能性がある場合、UTF-8 デコード成功 + HTML タグ不在で PNG 扱いになる誤判定が起きる (possible — 現状では問題ない)。
