# Lambda + Puppeteer HTML→PNG レンダリング (v2)

v1 で指摘した 5 件（Chromium バンドル、`networkidle0` タイムアウト、`needs_rendering` テスト欠如、Python 重複コード、BUCKET_NAME 不整合）はすべて修正済み。CDK コンストラクトに `nodeModules` 指定が入り、`waitUntil` は `domcontentloaded` に変更、Python 側は `_detect_content_type` ヘルパーに抽出、webhook テストに 3 ケース追加、BUCKET_NAME は全箇所 `process.env` 直接読みに統一された。

**Watch for:** レンダラ Lambda の `RENDERER_FUNCTION_NAME` がモジュールレベルで評価されるため、テスト時に `process.env` を差し替えても反映されない構造になっている (confirmed)。レンダリング後に旧 HTML オブジェクトが S3 に残り続ける (confirmed)。

## High-level view

`RENDERER_FUNCTION_NAME` は `shared/renderer.ts` のモジュールスコープで `process.env` から読み取り `const` に束縛される。本番環境では問題にならないが、テスト時に環境変数を差し替えても既にキャプチャされた空文字列が使われる。現在のテストはモック越しなので顕在化しないが、integration テストを書く際に壊れる地雷になる。

レンダラ Lambda は S3 上の `.html` キーを読み取り `.png` キーに書き出すが、元の `.html` オブジェクトを削除しない。プリントが生成されるたびに HTML ファイルが蓄積する。ストレージコストは微小だが、ライフサイクルポリシーか明示的な削除が欲しい。

## RENDERER_FUNCTION_NAME のキャプチャタイミング

```typescript
// shared/renderer.ts (module scope)
const RENDERER_FUNCTION_NAME = process.env.RENDERER_FUNCTION_NAME || "";
```

`invokeRenderer` 関数が呼ばれるたびに `RENDERER_FUNCTION_NAME` を参照するが、この値はモジュールロード時に固定される。webhook handler テストでは `vi.mock("../shared/renderer", ...)` でモジュール全体を差し替えているため問題が表面化していないが、もし将来 `invokeRenderer` のリアル実装を使う integration テストを書く場合、`beforeEach` で `process.env.RENDERER_FUNCTION_NAME` をセットしても空文字のままとなる。

対処は単純で、`invokeRenderer` 関数内で `process.env.RENDERER_FUNCTION_NAME` を読む形に変更するだけでよい（webhook handler 側の BUCKET_NAME と同じパターン）。

## S3 HTML 残留オブジェクト

レンダラ Lambda の処理フロー：

```
GetObject(prints/child-1/abc.html)
  → Puppeteer render
    → PutObject(prints/child-1/abc.png)
```

元の `.html` は削除されない。AgentCore が毎回新しい `print_id` を振るため上書きもされない。運用が長期化すると `prints/` プレフィックス配下に不要な HTML が蓄積する。CDK の `s3.Bucket` に `lifecycleRules` で `{ prefix: "prints/", tagFilters: { ... }, expiration: Duration.days(7) }` 等を設定するか、レンダラの最後に `DeleteObjectCommand` で明示削除するのが妥当。
